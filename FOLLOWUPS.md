- [x] P1 | 2026-08-09 | app/src-tauri/src/local_setup.rs:1195 | Elevated `wsl --install` is undiagnosable: `Ok(Ok(code)) => Ok((code, String::new()))` hands `classify_wsl_install` an EMPTY output string, because ShellExecuteEx("runas") gives no stdout/stderr pipe. So on the elevated path the text fallbacks (`contains("elevat")`, `contains("reboot")`) are dead code, and every code that is not 0/3010/1223/740 collapses to `StepFailed { exit_code, stderr: "" }`. HIT LIVE 2026-08-09 on Yossi's box: `wsl --install --no-launch -d Ubuntu` exited 1 after 23s of real work and the UI could only say "exit 1" — no reason, nothing in debug.log. The doc comment calls the lost pipes "an acceptable trade because the codes it does give us are unambiguous", but generic 1 is the common case and is exactly the ambiguous one. Fix: relaunch elevated via `cmd /c "wsl --install ... > %TEMP%\winmux-wsl.log 2>&1"` (or a ShellExecuteEx'd helper that redirects) and read the file back after the wait, so the real message survives. FIXED 2026-08-09 by fd1f537 — elevate `cmd /s /c` and redirect into a per-run temp file (path allowlisted by the new cmd_safe_path, WSL_UTF8=1 so the text is UTF-8), read it back after the wait, delete on every path. Exit code now logged on success too. Quoting verified against a real cmd.exe with --status swapped in for --install: redirect lands, 0 NUL bytes, real output captured. 5 new unit tests.
- [x] P1 | 2026-08-03 | app/src-tauri/src/lib.rs:1565 | emit_data strict-UTF8 decoder: if `leftover` starts with an invalid byte, `valid_up_to==0` returns WITHOUT draining -> that pane goes permanently silent and the buffer grows unbounded (no cap, no error branch).
